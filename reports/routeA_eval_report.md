# 路線 A 評估報告：Seed-VC 零樣本＋阿公片段微調

2026-10-11 · seedvc

## 結論

- **首選：v1（whisper-small-wavenet）用去噪片段微調 100 步**，配「去噪片段 06+08+07 串成的 22.7 秒參考音」、原音先把長停頓縮到 0.45 秒、擴散 100 步。對阿公去噪版前後半的聲紋相似度 **0.873**（同一人基準 0.901；零樣本 0.787），對原始錄音 0.737；F0 輪廓跟原音相關 0.77（聲調風險低）。試聽檔 `listen/B_v1ft_best.wav`。
- 跟計畫書的 kNN-VC（0.60–0.67，對原始錄音）比：**零樣本 v1 對原始錄音就有 0.794**，原始片段微調的 v1 達 0.862，都明顯高於 0.67（我們的同一人基準 0.939 與之前 0.92 只差 2%，門檻換算後 0.684）。
- **v2 不建議用在台語**：相似度較低（微調 500 步也只有 0.76–0.77），而且音高走向跟原音的相關只有 0.08–0.52（v1 約 0.77），convert-style 開時 0.08–0.29，台語聲調被改掉的風險高。
- **使用者聽到的兩個問題**：「語調平板、像導航」與「節奏不像阿公」主要來自原音。原音是網頁 TTS：字本身的速度跟阿公差不多（每秒 3.97 vs 4.13 字），但停頓比阿公長（平均 0.70 vs 0.44 秒，停頓比例 30% vs 22%），音高起伏也比阿公窄約 1 個半音。路線 A 只換音色，語調要靠換更好的 TTS 原音來改善（見 routeB）。縮短停頓可以讓節奏數字接近阿公，但改不了平板語調。
- **金屬／電子感**：只改推論設定（擴散 30／60／100 步、fp16 開關、cfg 0.7／0.4）時，高頻指標幾乎不變；擴散 100 步的數字最乾淨，但差異很小。換 44.1 kHz 聲碼器（音高條件模型）的數字沒有比較好。使用者確認去噪版、原始版的 agong_06 都沒有金屬感，所以去噪不是主因。剩下的可能是 22 kHz 聲碼器／擴散本身，或網頁 TTS 原音帶進來的質感，要用耳朵比 B 和 C 判斷（見第 6 節）。

| 轉換設定 | 未特別註明時：亂數種子 1234；v1 擴散 30 步、inference-cfg-rate 0.7、f0-condition False、fp16 True；v2 擴散 30 步、intelligibility／similarity cfg 0.7、top-p 0.9、temperature 1.0、repetition-penalty 1.0。每個存檔點都轉**同一段**原音。 |

**參考音重疊的影響**：①在原始錄音 37–50 秒，大部分落在「前半」（0–48.66 秒），所以用①時「前半」分數偏高，「後半」比較公平；②的片段分在 43–65 秒，兩半都有，用②時前後半分數比較平均。

- **原始片段微調的分數可能因為帶雜音而虛高**：它對「原始錄音」最高（0.862），是因為輸出學到了錄音的底噪與空間感，聲紋模型會把收音環境算進去；對去噪版反而較低（0.807）。不能直接說它「比較像」。
- 所有版本的音高跳動（0.002–0.03）、大聲字（0–1.8／10 秒）都不高於阿公本人（0.0156、2.06），只有 v2 400 步 style 開的跳動 0.031 高於阿公。
- v2 在 500 步時分數還在上升，但聲調風險高，照指示沒有再加訓。

- **音色**：微調（+0.05）和換成去噪參考音（再 +0.01～0.05）都讓「對去噪版」的分數上升；去噪參考音會讓對原始錄音的分數下降，因為輸出變乾淨了（預期中）。
- **音高區間**：阿公 12 段 F0 中位數 141.9 Hz，原音 137.8 Hz，只差 −0.5 半音（`eval/pitch_range.json`），沒有超過 1 個半音，所以**沒有做移調**。原音的音高起伏（P10–P90）7.6 半音，阿公 8.6 半音，原音比較平。
- **節奏**：差別主要在停頓，不在字的速度。只縮停頓（字不變速）後，語速 3.16–3.17、停頓比例 0.20–0.22，跟阿公（3.23、0.22）幾乎一樣，相似度不受影響；整段加速 1.16 倍則讓字念得比阿公快（構音 4.44 vs 4.13），停頓比例沒變，相似度略降。所以建議用「縮停頓」。但語調平板是原音的問題，縮停頓改不了。
- **v2 convert-style**：微調後 style 開的 F0 r 從零樣本 0.17 升到 0.24（最高 0.28），仍是高風險；語速沒有往阿公靠（2.84）。換參考音②反而更差。

- 擴散步數、fp16、cfg 對高頻指標的影響都很小（平坦度 0.028–0.030、尖峰度 31.8–32.5 dB）；擴散 60／100 步的相似度和高頻數字都略好，所以首選用 100 步（轉換時間約 2 分鐘）。
- 44.1 kHz 模型（換 BigVGAN 44k 聲碼器、跟著原音音高走）高頻數字沒有比較好，相似度也低；它的優點是聲調最貼原音（r 0.90）。
- 阿公錄音本身 4 kHz 以上能量就很少（原始 −34 dB、去噪後 −42～−48 dB），網頁 TTS 原音則很多（−10 dB）。這些指標只能看「高頻像不像雜訊」，沒辦法直接量到「金屬感」，請以耳朵比 B 和 C 為準。
- 還沒做、但最便宜的下一步：拿一段**真人錄音**（不是網頁 TTS）用同一設定轉一次。如果真人錄音轉出來就沒有金屬感，問題就在 TTS 原音。

- 桌面與其他程式平常就佔 1.6–2.6 GB。**使用者玩遊戲（League of Legends，約 1 GB 顯存）時，v1 微調會停住**（整張卡超過 8 GB），只能等遊戲結束重跑；推論（2–3 GB）在遊戲中仍可跑，但慢約 20–30%。兩次 v1 微調的時間差主要來自同時在跑的程式。
- 擴散步數加倍，轉換時間大約加倍；評估（CPU）每批約 2–3 分鐘。

## 6. 遇到的 Windows 問題與解法

1. repo 的 `requirements.txt` 同時寫了 nightly cu126 和 `torch==2.4.0`，互相矛盾 → 另外裝 torch，其餘依賴用 `routeA/setup/requirements-seedvc-win.txt`。
2. torch 2.4.0 在 Windows import 時報「Error loading fbgemm.dll」（缺 `libomp140.x86_64.dll`，要另裝 Visual C++ 套件）→ 改用 **torch 2.6.0+cu124**（與 envs/prep 相同）。torch 2.6 的 `torch.load` 預設 weights_only：已實測 Seed-VC 用到的所有權重和我們訓練的存檔點都能讀，不用改設定。
3. `resemblyzer`（只有 repo 的 eval.py 用）依賴 `webrtcvad`，Windows 要 MSVC 才能編 → 改裝 `webrtcvad-wheels`，再 `--no-deps` 裝 resemblyzer。
4. v2 推論用 pydub 串流成 mp3，需要 ffmpeg 在 PATH → 執行時把 `tools\ffmpeg\bin` 加到 PATH。
5. 沒裝 triton-windows、沒用 `--compile`（Windows 上避開 torch.compile）。注意 `inference_v2.py` 的 `--compile` 是 `type=bool`，給任何值都會變 True，不要傳。
6. Seed-VC 用相對路徑（`./checkpoints`、`configs/...`），必須在 repo 目錄執行 → `run_infer.py`／`train_keepall.py` 會自動切換目錄。
7. 訓練程式只保留最後 1–2 個存檔點 → `train_keepall.py` 攔截找舊存檔點的 glob，保留每 100 步的存檔點（代價：不能中途續訓）。`--num-workers 0`。
8. PowerShell 5.1 讀沒有 BOM 的 UTF-8 腳本會把中文當 ANSI → 所有 `.ps1` 都存成 UTF-8 with BOM。
9. 遊戲佔用顯存時訓練停住（見第 5 節）。

## 8. 還不能下的結論

- 全部數字都來自**同一段網頁 TTS 原音**。台語唸得對不對、聲調自然不自然，要會台語的家人逐句聽；F0 相關只是初篩。換成 routeB 的新原音後，請用 `convert_final.ps1` 重跑一次。
